The brief

Three questions, in order

A SOC proxy alert fires when a developer’s Linux workstation tries to upload an encrypted file to a file-sharing service. The developer says they were testing an AI tool for work. A triage package arrives: determine what AI tool was installed, what it was used for, and recover the data that was staged for exfiltration.

The three questions are not independent. Each one hands over the key to the next: the tool turns out to keep a prompt history, the prompt history contains a passphrase, and the passphrase — this is the whole puzzle — does not open the archive.

The title is the thesis. Whisper is what the developer believed they were doing: a local model, no vendor, nothing crossing the network. Ollama binds to 127.0.0.1:11434 and never phones home, so there is no provider-side transcript to subpoena. What there is instead is a plaintext readline history sitting in the home directory with no retention policy and no redaction.

Step 0 · Orientation

Find the ground truth before you look at anything else

The package ships /var/log/audit/audit.log and audit.log.1 — 16 MB, with a rule keyed exec_log. Every execve on the box is recorded with its full argv. That matters more than usual here, because ~/.bash_history is 0 bytes. The audit log is the only complete record of what this user ran.

var/log/audit/audit.log*12,729 EXECVE records

The mkdir/cp/du/cut mass is the triage collector copying the filesystem into /tmp/triage_root. Drop it and roughly 300 distinct command lines remain; filter those for the tool, the interpreter and the data paths and you are down to the two dozen that make the case.

Step 1 · Question one

The journal pins the version and the model: Listening on 127.0.0.1:11434 (version 0.30.8), general.name str = TinyLlama, running on CPU with a 2,048-token context. Loopback only — nothing about this install was ever going to appear in network telemetry.

What the journal does not have

The server config records OLLAMA_DEBUG_LOG_REQUESTS:false, and llama-server runs at --log-verbosity 4 — which logs token counts, slot scheduling and timings, but never prompt text. Grepping the journal for csv, zip, password or pyzipper returns nothing.

What it does give is the shape of the session: 17 × POST /api/chat between 12:01:08 and 12:45:38 UTC. Forty-four minutes of conversation, and not one word of it in the logs.

Step 2 · Question two

What it was used for

ollama run is a readline REPL, and like every readline REPL it persists its input to disk in cleartext: ~/.ollama/history. Sixty-four lines. Roughly sixty of them are exactly what the cover story predicts — logging config, FastAPI middleware, OpenTelemetry, postgres pooling, GitHub Actions caching. Genuinely useful questions, and the reason the file does not look interesting at a glance.

Six consecutive lines, buried mid-session, describing collection → encryption → exfiltration → anti-forensics. Line 32 — “show me how to create a zip archive in python” — is the hinge: the question before it is ordinary, the question after it is not, and nothing in between marks the turn. That gradient is why the file survives a skim.

The line that decides the case

Asking a model to write a CSV-archiving script is defensible — a data engineer might do that on a Tuesday. Asking it, in the same session, how to erase your shell history so there are no traces is not something anyone does by accident. Line 38 is what converts “testing an AI tool for work” into intent.

The history was edited before we got it

Its mtime is 12:57:59 UTC — twelve minutes after the last chat completion. The audit log says why: nano ~/.ollama/history at 12:55:12, cat at 12:56:38, nano again at 12:56:50. The file was reviewed and edited, so its contents cannot be assumed complete. What remains is still enough.

The library really was fetched

pip_packages.txt shows no pyzipper on the system interpreter, because it was installed elsewhere. But pip’s HTTP cache under ~/.cache/pip/http-v2/ still holds the downloaded wheels, and wheels are ordinary zip files:

pyzipper and requests — exactly the two dependencies lines 33 and 36 called for.

Step 3 · Recovery

The deleted script was never deleted

audit EXECVE2026-06-16, UTC
12:58:20  python3 -m venv /home/dwright/.local/share/.venv   ← dotted = hidden
12:59:43  python /home/dwright/cache_mgr.py

Two details. The venv is dotted — .venv inside ~/.local/share, where nobody scrolls — which is why the system pip list comes back clean, and why the script has to sys.path.insert it by hand. And the prompt asked the model to delete the script after execution; what actually happened was a GNOME Trash move. The file is still on disk, byte for byte.

Even without the audit log, the Trash gives it up on its own. Each item carries a .trashinfo with its original path and deletion time, so sort by date:

The passphrase is not the password

A single non-font file in a font cache is already an anomaly, and WinZip-AES encrypts data but never filenames — so the manifest reads in the clear. Five members; /data/reports/ holds four. The audit log closes the gap:

audit EXECVE60 seconds apart

13:00:43  rm -f /data/reports/internal_api_keys.csv  ← destroys the 5th

Archived first, rm’d from disk one minute later — and rm, not trashed, so there is no second copy. The only surviving internal_api_keys.csv anywhere in the evidence is the encrypted one. That is the challenge in a sentence.

Three ways to get the password wrong

The obvious move fails, and so does the one the history points at. Line 37 asked about hashlib sha256; the code the model returned uses BLAKE2b. The prompt records what the user asked for, not what they got.

Passphrase · history line 35 Gr33nF0x42!D1amond
The red herring sha256(passphrase)
What the code does blake2b(…, digest_size=32).hexdigest()
Archive password · first 20 hex chars d571fe77618f54b7fca8

Three places to slip: the wrong hash function, the raw digest instead of its ASCII hex rendering, and the truncation to twenty characters. All three have to be right at once.

Reading the container instead of trusting a tool

extra field 0x9901WinZip AE-2
01 99  07 00  02 00  "AE"  03  08 00
^^^^^  ^^^^^  ^^^^^        ^^  ^^^^^
hdr    len    AE-2        AES-256  deflate

CRC-32 in the central directory: 0x00000000  (all five members)

AE-2 zeroes the CRC by design and verifies with a truncated HMAC-SHA1 over the ciphertext instead. A solver that checks CRC will report failure on a perfectly good decrypt. Key material is PBKDF2-HMAC-SHA1(password, salt, 1000, 2·32+2) → AES key ‖ HMAC key ‖ 2-byte verifier, and the cipher is AES-256-CTR with a little-endian counter starting at 1.

Step 6 · Cleanup

Five anti-forensic moves, none of which worked

Line 38 of the prompt history was acted on. Here is what was tried, and why the evidence survived it.

TechniqueEvidenceWhy it failed
Shell history wiped ~/.bash_history is 0 bytes auditd was logging execve under a rule keyed exec_log. Clearing bash’s own file removes one copy of the record, not the record.
Script “deleted” mv to ~/.local/share/Trash/files/ A Trash move is not a delete. The file, its original path and its deletion time all persist — and that timestamp made it the standout item in a 59-entry Trash.
Archive disguised ~/.cache/fontconfig/session.zip Font caches hold .cache files, not zips. One file of the wrong type in a well-known directory is louder than an odd filename somewhere unremarkable.
Venv hidden ~/.local/share/.venv (dotted) pip’s HTTP cache kept the downloaded wheels regardless, naming pyzipper and requests outright.
Decoy files 8 × dd if=/dev/urandom into /tmp at 13:00:48 UTC, plus 3 stubs All eight created in the same second, every one bs=1024 with a round count — and each dd command line sits in the audit log with its exact output path.

The decoys are named to bait the first grep an analyst runs: .config_backup_old.tar.gz, .mozilla_cache.dat, .pip-cache-a8f3b2.tmp, .wget-download-c4e2f1.tmp, journal-upload.tmp, core.python3.1234.1781614848. Eight are pure /dev/urandom; the other three are jokes small enough to cat — .viminfo.tmp is the seventeen bytes temporary buffer, and __pycache__/tempmod.cpython-312.pyc is nine bytes reading compiled, where a real .pyc starts with a magic number. You do not have to guess whether they matter. The audit log says they were manufactured.

A timestamp that does not survive scrutiny

session.zip’s own mtime and all five member timestamps read 2026-06-20, ~15:42–15:45 local — four days after the incident. But the containing directory ~/.cache/fontconfig/ has mtime 2026-06-16 12:59:43 UTC, matching the audit log’s python cache_mgr.py to the second.

Directory mtimes update on file creation and are not what a naive timestomp touches, so the directory and the audit log are the trustworthy pair. It changes nothing about the conclusion — but a report quoting the zip’s internal dates as the time of the offence would be quoting forged data.

On the proxy alert

Inside this package, transfer.sh appears in exactly one place: the recovered script. There is no proxy log, no netflow, no HTTP cache artefact. The attempt is established by the script and the audit log; the alert itself is context from the brief rather than something the evidence proves. Whether the PUT ever succeeded cannot be determined here at all — the script swallows every exception the upload raises.

Closing

What this case is actually about

A local model is not a forensic void

The entire premise of running Ollama on a workstation is that the conversation never leaves the machine: no provider transcript, no DLP on the wire, nothing for legal to subpoena. That is true, and it is exactly why the artefacts are better. ~/.ollama/history is a plaintext, user-readable record of every prompt, with no retention policy and no redaction. A cloud provider would have given you a subpoena and a metadata dump. The local install gave you the words.

Prompt histories are intent, and intent is the hard part

The technical acts here are individually innocent and individually deniable: write a zip, upload a file, clear a history. What is not deniable is the sequence, in the user’s own words, timestamped, in one session. No amount of binary analysis produces that. It is the difference between proving what happened and proving why.

Read the code, not the request

The SHA-256 prompt works as a trap because it is a reasonable thing to believe. The user asked for SHA-256; the model wrote BLAKE2b; nobody checked. A chat log is a statement of intent and nothing more — when the recovered artefact contradicts the prompt that produced it, the artefact is the fact.

For the defensive side

Three controls would each have caught this independently: egress filtering on public file-sharing hosts, DLP on /data/reports reads by non-service accounts, and — the cheap one — treating local LLM installs as a monitored category rather than shadow IT. Ollama installs with a curl | sh from a normal user account into /usr/local, registers a systemd unit, and never touches the package manager. It is invisible to dpkg, invisible to pip, and it is where the confession ended up.
